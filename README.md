# AI Trading System

Paper-only мультивалютная спотовая система. Фазы 1–6: учёт, риск, симулированный стакан, сетка, mock-новости, paper A/B, рантайм с дашбордом, стресс-сценарии, Telegram-управление. Реальных ордеров нет. Доходность не обещается.

## Быстрый старт для тестирования

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest                                   # полный набор; 24/7: docs/RENDER.md, свой Linux: docs/VPS.md

# 1. Офлайн-прогон на синтетической ленте (без сети, без UI), 600 шагов по 5 с модельного времени
python -m app.cli run --config configs/paper.wide.example.yaml --steps 600

# 2. Дашборд: собрать фронтенд один раз, затем поднять API с фоновым циклом
(cd frontend && npm install && npm run build)
ATS_RUN_LOOP=true uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
# открыть http://127.0.0.1:8000/

# 3. Публичный стакан Binance (только GET, без ключа) вместо синтетики
ATS_EXCHANGE=binance_public ATS_RUN_LOOP=true uvicorn app.main:app --app-dir backend --port 8000
```

После `pip install -e .` пакет `app` импортируется из любого каталога, поэтому `python -m app.cli` работает и из корня. Состояние лежит в `local.db` (новости), `local.baseline.db`, `local.ai.db` в текущем каталоге. Перезапуск продолжает счёт с того же места: лоты и резервы восстанавливаются из журнала, отдыхающие ордера пересоздаются по тем же `client_order_id`. Удалить файлы — начать с нуля.

Что ждать от конфигов:

- `configs/paper.example.yaml` — шаг 0,30% из ТЗ. После slippage чистый остаток 0,05 < цель 0,10, сетка **не входит**. В Risk & Logs будет `below_net_target`. Это намеренно оставленный край.
- `configs/paper.wide.example.yaml` — шаг 1,00%, остаток 0,75. Сетка входит, циклы появляются. На синтетике обе копии дают одинаковый equity, пока нет новостных событий.
- `configs/paper.binance_public.usdt.yaml` — реальные котировки Binance (GET), 1 000 USDT, шаг 0,50%, BTC/ETH/SOL/XRP, ≤ 3 активных пар, ≤ 30% в позициях; БД и лог в `var/` (в gitignore). Запуск: `python -m app.cli serve --config configs/paper.binance_public.usdt.yaml --port 8000`.
- Новости по умолчанию отсутствуют. `ATS_NEWS_FIXTURES_PATH=configs/news.fixtures.example.json` подмешивает помеченную иллюстративную фикстуру: AI-копия ставит паузу покупок по SOL на 600 с, baseline нет.

Кнопки: `PAUSE NEW BUYS` запрещает новые покупки обеим копиям, выходы остаются. `HALT ALL` дополнительно снимает отдыхающие покупки. `STOP & LIQUIDATE` активна только после ввода `CONFIRM_LIQUIDATE`, снимает выходы и продаёт по bid — может закрыть с убытком. `TICK` делает ручной шаг и отклоняется (409), пока работает фоновый цикл.

Параметры рантайма, которых нет в таблице ТЗ: `market_poll_interval_sec` 5, `synthetic_seed` 7, `exchange: simulated|binance_public|disabled`. Синтетика — случайное блуждание от 100 с шагом 0,05% и глубиной 5 уровней по 10 единиц; это проверка проводки, не рынок.

Корень репозитория — проект из ТЗ (`ai-trading-system/` в спецификации). Live-отправка ордеров не реализована и в этой сборке отклоняется.

## Что делает фаза 1

Один ledger на весь бумажный счёт. Валюта котировки задаётся конфигурацией: `USDC`, `USDT` или `EUR`, не зашита как USDT. Покупка сначала резервирует quote, fill создаёт отдельный лот. Комиссия в базовом активе уменьшает объём, который можно продать. Продажа не может закрыть больше остатка своего лота. Повтор того же `client_order_id` или `fill_id` не списывает деньги второй раз.

Equity в валюте котировки:

`free quote + reserved quote + profit reserve + bid × остаток лота − оценка exit fee`

Открытая позиция не считается уже проданным стейблкоином. Realized P&L появляется только после sell fill.

Risk manager отделён от текста модели. Он резервирует бюджет и может отказать. LLM-схема не содержит `place_order` и не содержит вероятность движения цены. Невалидный или посторонний JSON переводится в `pause_new_buys`. Без API-ключа клиент модели не отправляет запрос.

`LiveAdapter.place_order`, `cancel_order` и `withdraw` всегда поднимают ошибку и не сохраняют ключ. `PaperAdapter` без ledger/risk тоже ничего не отправляет. С подключённым ledger он матчит лимитку только по локальному стакану: не больше видимой глубины, проскальзывание не пробивает лимит, частичный fill оставляет остаток в резерве. Повтор `client_order_id` не создаёт второй ордер. `UNKNOWN` сверяется с локальным состоянием и не уходит в `SUBMITTED`.

## Поток решения

```text
стакан (bid/ask/глубина)
    -> GridStrategy (intent, без ордера на биржу)
    -> RiskManager
    -> PaperAdapter
    -> ledger fill
    -> equity

LiveAdapter  --x  биржа
LLM output   --x  place_order
```

Сетка ставит buy на `grid_step_pct` ниже якоря и sell по цене, которая после фактической комиссии входа, комиссии выхода, slippage и `net_target_pct` ещё неотрицательна. Если шаг не покрывает цель, новых покупок нет: пример 0,30% при комиссиях 0,10% + 0,10% и slippage 0,05% даёт 0,05 и не входит. Выходы по уже открытым лотам считаются отдельно.

Baseline и AI — две копии с одним и тем же стартовым кэшем и одним и тем же стаканом. Внутри одного ledger две заявки не тратят одни и те же деньги. Новостной `PAUSE_BUYS` режет только AI. Ручной pause запрещает новые покупки обеим, выход остаётся. `STOP & LIQUIDATE` по-прежнему требует `CONFIRM_LIQUIDATE`; paper может исполнить такой sell только если его отдельно отправить в `PaperAdapter` и в стакане есть bid.

Жёсткие фильтры вселенной (статус рынка, quote, watchlist, spread, глубина, min notional, tick, lot, недавний листинг) считаются локально, без сети. Стартовый список: BTC, ETH, SOL, XRP, BNB, LINK, ADA, AVAX.

## Конфиг примера и чистый край

В `configs/paper.example.yaml` шаг 0,30%, две комиссии по 0,10% и slippage 0,05%.

`0,30 − 0,10 − 0,10 − 0,05 = 0,05` процентного пункта.

`net_target_pct` в том же файле равен 0,10. После slippage пример **не достигает** цели. До slippage остаток как раз 0,10. Если slippage больше остатка, круг убыточен. Параметры не менялись: это арифметика файла. Проверка — `round_trip_net_pct` / `meets_net_target`.

Отдельно от таблицы ТЗ в example-файле заданы предохранители, их можно сменить явно:

| ключ | значение | смысл |
| --- | --- | --- |
| `market_stale_after_sec` | 15 | нет новых заявок, если книга старше |
| `max_spread_pct` | 0,50 | отказ при более широком spread |
| `depeg_max_deviation_pct` | 1,00 | отказ новых покупок при отклонении котировки от её peg |
| `max_drawdown_pct` | 10 | отказ новых покупок |
| `profit_reserve_pct` | 0 | доля realized прибыли, уходящая из free в Profit Reserve (новые покупки её не тратят) |

Peg считает вызывающий код. Для USDC/USDT это отклонение от 1. Для EUR это не «курс к доллару», а отклонение от того peg, который передали в риск.

`reduce_size` без явного множителя не уменьшает ордер сам: покупка отклоняется. Множитель в конфиг не зашит.

## Режимы

| режим | статус |
| --- | --- |
| Paper ledger + matching по локальному стакану | есть |
| Paper forward на публичном стакане | есть, `exchange: binance_public`, только GET |
| Исторический backtest | не начат; тем же ledger, без новостей «задним числом» |
| Биржевой demo / testnet | не подключён. Demo-ордер не равен этой симуляции и не является live |
| Live | выключен. Ключ Trade+Read без Withdraw — только после отдельного запроса и gate из ТЗ |

Даже прибыльные недели paper не доказывают будущий результат. USDC/USDT не являются наличными евро: остаются риск эмитента, depeg и площадки. Конкретную пару нужно сверять с доступом аккаунта (в ЕЭЗ USDT может быть недоступен).

## API

Без маршрута ордера. `GET /health`, `GET /api/state` (всё разом), `/api/markets`, `/api/news`, `/api/lots`, `/api/trades`, `/api/working`, `/api/ab`, `/api/decisions`, `/api/equity?limit=N` (ряд equity по копиям из БД); `POST /api/controls/pause|halt|resume`, `POST /api/controls/liquidate {"confirmation": "CONFIRM_LIQUIDATE"}`, `POST /api/tick`. Decimal отдаётся строкой. Ключи в ответах не появляются (есть тест).

Дашборд собирается в `frontend/dist` и раздаётся тем же процессом с `/`. Для разработки UI: `cd frontend && npm run dev` (прокси на 8000).

PostgreSQL через Compose, процесс по-прежнему paper:

```bash
docker compose up --build
```

Docker на этой машине не установлен: образ и Compose не запускались. В Postgres каждая копия пишет в свою схему (`baseline`, `ai`), новости — в `public`; на SQLite это три файла. Секреты только в незакоммиченном `.env` (см. `.env.example`). Пустой ключ не приводит к сетевому вызову.

Миграция:

```bash
cd backend
alembic -x url=sqlite:///./local.db upgrade head
```

## Новости (фаза 3)

Только фикстуры `MockNewsSource`. HTTP-клиента нет, заголовок в тесте — не рыночное событие. Опрос не чаще раза в 60 секунд. Пустой ответ и текст без монеты и без рыночного слова в модель не отправляются.

Десять перепечаток — одно событие и несколько ссылок. `first_seen_at` не сдвигается, `published_at` хранится отдельно. Одинаковая ссылка после отрезания `utm_*` и фрагмента не становится вторым событием. Похожий текст (пересечение токенов 4/5 и выше) тоже склеивается.

Вес: 1 в секунду `first_seen_at`, дальше линейно до 0 за `news_stale_after_sec` (в примере 600). На нуле событие больше не задаёт режим. `MARKET` действует на все символы. Более строгий режим побеждает. Перепечатка вес не обнуляет.

Имена стартового списка: solana → SOL и остальные полные имена. `SEC` и depeg без своей монеты → `MARKET`. Взлом площадки → `MARKET` и названные тикеры; слово binance само по себе не становится BNB. `one` не тикер. `$ONE` и `ticker ONE` учитываются только если ONE есть в watchlist. То же для ALL, FOR, NOW, AIR, DATA. Текст статьи сохраняется и не исполняется. Нет разбора модели — пауза покупок для AI.

Статус площадки — готовый снимок, без запроса наружу. `suspended` и неизвестный статус дают `EXCHANGE_ISSUE`, даже если лента пустая. Пустой список активов — на все символы, иначе только на перечисленные.

## Рынок и paper A/B (фаза 4)

Публичное чтение стакана — только `GET` на `api.binance.com`: `depth`, `bookTicker`, `trades`, `klines`, `exchangeInfo`. Это не выбор площадки для ордеров и не ключ. `USDT` в символ не подставляется: пара берётся из base/quote, в том числе `EUR`. Чужой host, путь с `order` и подписанный query отклоняются до запроса. Тесты подставляют транспорт и сеть не открывают.

Свеча 1m считается только в ATR (окно 14). Из свечи книга не строится. Кадр с дельтой стакана (`b`/`a` без полного `bids`/`asks`) книгой не считается. Задержка кадра — от метки `E` до времени приёма.

`run_ab` гоняет baseline и AI на одной ленте книг и двух одинаковых бумажных счетах. Счёт сравнения — equity после комиссий. Отдельно пишутся случаи, где пауза AI не дала купить то, что у baseline ушло в минус, и где та же пауза пропустила его плюс. Шаг 0,30% из примера по-прежнему не входит ни в одну копию.

## Рантайм и дашборд (фаза 5)

`PaperRuntime` держит две копии — `baseline` и `ai` — на одной ленте книг и одинаковом стартовом капитале. Каждый шаг: опрос новостей (не чаще 60 с), книга по каждой паре, жёсткий фильтр вселенной, контекст риска (свежесть, spread, peg, статус рынка, режим новостей для base-актива, ручные флаги), `GridStrategy.sync` → `RiskManager` → `PaperAdapter`, переоценка equity по bid, запись в БД. Решения риска пишутся в журнал одной строкой на интент; повтор одного и того же отказа складывается в счётчик. Журнал и поминутный ряд equity (на каждый тик) сохраняются в БД копии и переживают рестарт. Для `binance_public` книга считается устаревшей, если её `lastUpdateId` не менялся дольше `market_stale_after_sec`.

Количества fill квантуются до 1e-8, как на площадке; остаток бюджета меньше 1e-6 quote возвращается в free, иначе тождество кэша расходится в 28-м знаке. После рестарта якорь сетки и отдыхающие заявки читаются из `strategy_anchors` / `working_orders`: лимитная цена не пересчитывается от текущего ask. Стратегия двигает якорь только своим правилом (ниже входного fill). Выход по лоту с активным hold предлагается тем же `client_order_id`.

Стресс-сценарии (`backend/tests/test_stress.py`) гоняются через тот же рантайм: −15% за минуту (лимиты 6 лотов / 15% на актив держатся, тождество кэша выдерживается), drawdown-gate, ложный твит (пауза только у AI, истекает через 600 с), взлом площадки (`HALT_ALL`: AI не покупает и не ставит обычный выход, подтверждённая ликвидация проходит), outage ленты (обе копии замирают без ошибок), запоздавшая новость (`published_at` ≠ `first_seen_at`), depeg (обе копии), делистинг/halt рынка, частичный fill на закрытии (остаток в hold), pause/halt/resume, рестарт из БД без второго лота, JSON без секретов.

Peg для `binance_public`: отклонение mid USDC/USDT от 1 как прокси; для EUR peg не считается (0). Это прокси, а не оракул.

## Telegram (фаза 6) — отдельный процесс, только чтение

Бот на aiogram 3 с long polling — **отдельный процесс**. К торговому движку он ходит только через локальный `GET http://127.0.0.1:8000/api/state`. Второго PaperRuntime нет, БД торговли не открывает, `LiveAdapter` не импортирует. По умолчанию управление (pause/halt/resume) **выключено**. Ликвидации и ордерных маршрутов нет. Один polling на токен: `var/telegram.<hash>.lock`.

Команды: `/whoami` (свой user id, без торговых данных, работает и без allowlist), `/start` главная, `/status` (источник рынка и время обновления стакана), `/balance` (free / reserved / Profit Reserve, realized, unrealized, equity), `/positions`, `/trades`, `/news` (источник, ссылка, published/received, TEST/MOCK, не выдаёт mock за LLM), `/report` (A/B). Группы игнорируются.

Уведомления: BUY/SELL из ledger, закрытый цикл с P&L, критичный режим риска, пропажа ленты, ошибка процесса, просадка выше `telegram_drawdown_alert_pct` (5%), отключение и восстановление локального API. Дедуп, лимит в минуту, часовая сводка, файл `var/telegram_state.json` — после рестарта бота старые сделки не рассылаются.

### Как подключить (токен в чат не вставлять)

1. @BotFather → `/newbot` → токен сохранить только в `.env`.
2. Скопировать `.env.example` в `.env` в корне репозитория. Вписать токен и (пока пустой) allowlist:

   ```
   TELEGRAM_BOT_TOKEN=123456:AA...
   TELEGRAM_ALLOWED_USER_IDS=
   ```

   Те же ключи принимают префикс `ATS_`.
3. Узнать user id: запустить бота и написать ему `/whoami` (или @userinfobot). Число вписать в `TELEGRAM_ALLOWED_USER_IDS`.
4. PaperRuntime уже должен слушать 8000. **Не** поднимать второй `serve`.
5. Проверка доставки и выход:

   ```bash
   python -m app.telegram --test-message
   ```

6. Постоянный процесс (своя сессия, не трогает торговлю):

   ```bash
   python -m app.telegram
   ```

   `/start` должен показать обе копии из той же БД. Остановка: Ctrl-C. Второй экземпляр с тем же токеном сразу выйдет (код 3).
7. Автоперезапуск на Mac (после того как `.env` заполнен): `launchctl load ~/Library/LaunchAgents/com.ats.telegram.plist` — пример plist в `scripts/com.ats.telegram.plist`. Если Mac засыпает, и торговля, и бот останавливаются. Круглосуточно — Render (`docs/RENDER.md`) или Linux VPS (`docs/VPS.md`). Реальный сервер из репозитория сам не поднимается.

Резервная копия БД (живой процесс не останавливает):

```bash
python -m app.cli backup --config configs/paper.binance_public.usdt.yaml --dest var/backups
```

Второй `python -m app.cli serve` на ту же `database_url` сразу выходит: lock в `var/paper.<hash>.lock`.

## Наблюдение 24 часа

Только GET к уже идущему API, без второго рантайма и без смены сетки:

```bash
python scripts/paper_watch.py --minutes 1440 --interval 60 \
  --out reports/PAPER_24H_REPORT.md --samples var/watch_24h.jsonl \
  --checkpoint-dir reports/hours
```

Каждый час пишется `reports/hours/hour_NN.md` (дистанция bid до ближайшей покупки по каждой монете). Итог за сутки — `reports/PAPER_24H_REPORT.md`.

## Не сделано

- Исторический backtest и replay по архиву с доказанным временем доступности новости.
- Реальные источники новостей и реальный LLM-коннектор: клиент есть, без ключа запрос не уходит, реальный вызов не включён.
- Корреляция активов как модель; есть только портфельный лимит.
- Лимитная цена сетки не квантуется под `tick_size` площадки (в paper это не мешает, на реальной бирже ордер отклонили бы).
- Postgres-режим Compose не запускался (нет Docker на машине).
- Telegram Mini App. Доставка живого сообщения в Telegram — после токена в `.env` и `python -m app.telegram --test-message`.

Live не включается переходом между этими фазами.
